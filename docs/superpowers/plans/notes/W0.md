## The 7a review (base 81abfff; a reviewer subagent, checked by hand)

### Important, fixed

1. **A run could stay queued or running for good.** This happened when the process stopped,
   Trigger.dev never ran the task, or the task hit its `maxDuration`. The run then held the
   one-in-flight indexes, so uploading again (the documented retry) answered "running" forever,
   and the course's top-ups answered "busy".

   The fix: before starting a job, `startUploadJob` and `startTopUpJob` mark the student's
   queued or running runs failed when they're older than the job's `maxDuration` plus 10 minutes.
   That's the material's runs for an upload and the course's runs for a top-up. The error is
   "Orca's job stopped without finishing. Upload the file again to retry." `waiting` runs (the
   daily limit) are never treated as dead. `JOB_MAX_SECONDS` is shared with `src/trigger/jobs.ts`.

2. **A missing or invalid `ORCA_JOBS` was checked after the run row was inserted.** The route
   then answered 500 and left a queued run behind. The mode is now checked before anything is
   written. A failed hand-off also says when marking the run failed itself fails.

3. **`fail()` could turn a done run into failed** (promoted from Minor: it's a cost leak). If the
   structure save landed but its reply was lost, the run was marked failed. The next upload then
   rebuilt the material, paid again and duplicated its questions. `fail()` now only touches a run
   that's in flight. There's a unit test for it.

### Small fixes made in passing

- `answered()` pages over `order("at").order("id")`, so it no longer skips rows past 1,000 answers.
- The add-material page opens the review screen for a file whose questions were already built.
  It used to say "No AI is connected", a placeholder that wasn't true.
- `check:evidence` was broken since Task 6: students can't set a material's `storage_path` any
  more. Its material is now a record without a file.

### Minor, not fixed (for the owner, 9b or the workstream named)

- **Changed-column saves still lose concurrent writes to the same column** (B or A, or a
  follow-up). The job's `before` is read when the job starts:
  - aliases: a student merge and an upload attaching to the same survivor both write the whole
    `aliases` array;
  - layout: `laidOut()` positions are recomputed on both sides.

  The status block's "don't overwrite each other" holds only for different columns. Fix: re-read
  and re-apply the plan just before saving, or append aliases in SQL.
- **A `refresh()` that lands mid-edit can drop an optimistic change from the screen** (D, store).
  The change is still saved; it reappears on the next load (`store.tsx` around 601–612).
- **A session can be topped up any number of times** (B). Nothing ties a top-up run to its
  session. 7c's budget bounds the cost; a `session_id` on the run with a unique index would close
  it.
- **`useRun` keeps polling, and stays subscribed, after the run finishes.**
- **`src/lib/server/jobs/run.ts` reaches `next/headers`** through `adminClient`
  (`@/lib/supabase/server`), despite its header. Check the Trigger.dev worker build in Task 10, or
  move `adminClient` to a module without Next.js imports.
- **`/api/reflect` sends an empty topic name** (`?? ""`) when an objective's topic is missing. A,
  since it owns that route now.
- **Kind mismatch in `begin()`:** a run of the wrong kind throws, so the run is marked failed.
  With the new status guard this only hits a run that's still in flight.

## Judgement calls and differences

- **The start decisions moved into `src/lib/jobs/start.ts`** (Node-loadable, with the database
  and the dispatch passed in), so they can be unit-tested with a fake database.
  `src/lib/server/jobs/start.ts` keeps the same exports (`startUploadJob(db, owner, id)`,
  `startTopUpJob`, `jobsMode`) and wires in `after()`, Trigger.dev and `serverModel()`.
  `MaterialJob`/`TopUpJob` now live in `src/lib/jobs/start.ts`, re-exported from `run.ts`.
  **B owns both files from here.**
- **Dead runs are detected by age (`at`), not by a heartbeat**, so no migration was needed.
  - The cut-off is the task's `maxDuration` plus 10 minutes: 40 minutes for an upload, 25 for a
    top-up.
  - **Note for B:** once runs queue one at a time per student, a run can be legitimately queued
    for longer than that. Measure age from the claim (or add a heartbeat), or leave queued runs
    to your own sweep.
  - An inline job is cut off at its route's 300 s, so locally a dead run blocks retry for up to
    40 minutes. That's acceptable for dev.
  - In production with `ORCA_JOBS` unset, the upload route now fails outright (500), even
    without a model key. That's on purpose: production must set it.
- **`untrustedBlock` output** is `{"source":…,"content":…}` on one line. JSON escapes quotes,
  backslashes and newlines. Format characters, the tag block (U+E0000–E007F) and U+2028/2029 are
  also written as `\u` escapes, so nothing invisible reaches the model literally. `<` and `>` are
  left as they are, since a tag inside a JSON string can't close anything. A can wrap blocks
  however its prompts need.
  - `UNTRUSTED_POLICY` follows decision 13's wording and names the four sources.
  - The block refuses `undefined`, functions, cycles and BigInt.
- **`ModelCtx` lives in `model.ts`.** `llm-server.ts` imports it type-only, so
  `score-extraction` still loads under Node; `--dry` was checked. `/api/grade` and
  `score-extraction` call `completeJson` without a ctx (Task 8 adds `grade`).
- **The stack lock** is `/tmp/orca-supabase-stack.lock` (`ORCA_STACK_LOCK` overrides it).
  - The default timeout is 3600 s (`ORCA_LOCK_TIMEOUT`).
  - A lock whose PID is dead, or that has had no owner file for 30 s, is taken over by renaming
    it first.
  - The command runs in its own process group, which is stopped on INT, TERM or HUP.
  - Tested by hand: three at once queue in turn, a stale lock is taken over, a live holder times
    out with exit 75, and TERM releases the lock and kills the child.
- **Environment:** this Mac's default `node` is v16, so the npm scripts that need type stripping
  fail with "bad option". Run with Node 24 (`~/.nvm/versions/node/v24.20.0/bin`) or `nvm use`.
  This is noted in README.md.
